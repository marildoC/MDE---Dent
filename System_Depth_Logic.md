## 1. System Identity
- DentCare-MDE is a model-driven dental follow-up system.
- The implemented clinical domain is post-extraction follow-up.
- The only implemented treatment type in `TreatmentType` is `POST_EXTRACTION`.
- DentCare-MDE is not implemented as a generic dental chatbot.
- DentCare-MDE is not implemented as an open-ended natural-language diagnosis assistant.
- DentCare-MDE uses structured patient reports instead of free-form symptom interpretation.
- DentCare-MDE uses configured workflow models to determine follow-up behavior.
- The workflow model is the central artifact of the system.
- The workflow model defines care stages, symptom vocabulary, symptom rules, advice boundaries, and escalation rules.
- A workflow can be created, validated, activated, and archived.
- An active or archived workflow can be moved back to `DRAFT` through the explicit Edit lifecycle action.
- Only an active workflow can be assigned to a patient follow-up case.
- A follow-up case links a patient profile to a workflow and a treatment date.
- The active workflow controls runtime behavior through the `FollowUpCase.workflow` relationship.
- When a symptom report is submitted, the decision engine reads the workflow assigned to that report's follow-up case.
- The decision engine does not search all workflows.
- The decision engine does not select a workflow by natural language.
- The decision engine interprets the workflow already assigned by staff/admin.
- The system does not autonomously diagnose dental disease.
- The system does not prescribe medication.
- The system does not interpret dental images for diagnosis.
- Uploaded images are stored as optional supporting evidence on `SymptomReport.image`.
- The implemented output is risk assessment, patient-facing guidance, escalation, appointment priority, and audit traceability.
- Dental staff remain responsible for clinical judgment.
- The patient sees bounded guidance, not a diagnosis.
- The staff/admin side sees the runtime objects created from the model interpretation.
- The implemented model-driven behavior is concentrated in workflow validation and report assessment.
- The workflow model is therefore more important than any single report screen.
- The runtime engine treats the workflow as a model to interpret.
- A symptom report acts as an input instance for the active model.
- The patient symptom report form is generated from the assigned workflow's symptom definitions when definitions exist.
- Dynamic symptom values are persisted in `SymptomReport.symptom_values`.
- Legacy fixed symptom fields remain for backward compatibility with older reports and older UI logic.
- A risk assessment acts as a persisted interpretation result.
- Advice, escalation, appointment handling, and audit logs act as downstream runtime artifacts.

## 4. Workflow Model And Internal DSL
- The internal DSL is implemented through Django model classes rather than an external parser.
- `TreatmentWorkflow` is the root model artifact.
- `CareStage` represents a named recovery period inside a workflow.
- `SymptomDefinition` represents a symptom vocabulary item for a workflow.
- `SymptomRule` represents structured decision logic attached to a care stage.
- `AIAdviceBoundary` represents patient-facing advice safety constraints.
- `EscalationRule` represents the configured staff-escalation requirement linked to a symptom rule.
- `WorkflowStatus` represents lifecycle state.
- `WorkflowStatus` values are `DRAFT`, `VALIDATED`, `ACTIVE`, and `ARCHIVED`.
- `TreatmentWorkflow.name` identifies the workflow.
- `TreatmentWorkflow.treatment_type` identifies the domain treatment type.
- `TreatmentWorkflow.description` gives optional model documentation.
- `TreatmentWorkflow.created_by` links the model to the user who created it.
- `CareStage.workflow` attaches a stage to its workflow.
- `CareStage.name` identifies the recovery interval.
- `CareStage.start_day` and `CareStage.end_day` define the inclusive day range.
- `CareStage.sort_order` controls ordering where multiple stages exist.
- `CareStage.description` stores optional recovery-stage explanation.
- `SymptomDefinition.workflow` attaches a symptom to a workflow.
- `SymptomDefinition.key` is the symbolic DSL field name.
- `SymptomDefinition.label` is the human-facing label.
- `SymptomDefinition.data_type` can be `INTEGER`, `BOOLEAN`, `CHOICE`, or `TEXT`.
- `SymptomDefinition.allowed_values` stores possible values for choice-style symptoms.
- `SymptomDefinition.min_value` and `max_value` exist in the backend model.
- The current workflow detail form does not visibly expose min and max value inputs.
- `SymptomDefinition.is_required` marks whether the symptom is required in the model.
- The current runtime report form is dynamically generated from workflow symptom definitions.
- `SymptomReport.symptom_values` stores the dynamic input values as JSON.
- The fixed report fields `pain_level`, `swelling`, `bleeding`, `fever`, and `bad_smell` are still present for backward compatibility.
- Legacy fixed fields are populated only when submitted workflow values are compatible with their old field constraints.
- Workflow-specific values such as `MODERATE`, `HEAVY`, or `SPOTTING` remain in `symptom_values` when the old fixed field cannot accept them.
- `SymptomRule.stage` attaches a rule to exactly one care stage.
- `SymptomRule.condition` is structured JSON.
- `SymptomRule.risk_level` can be `LOW`, `WARNING`, `HIGH`, or `URGENT`.
- `SymptomRule.recommended_action` can be `SHOW_ADVICE`, `CONTINUE_MONITORING`, `RECOMMEND_CONTACT`, `ESCALATE_TO_DENTIST`, or `PRIORITIZE_APPOINTMENT`.
- `SymptomRule.appointment_priority` can be `NONE`, `LOW`, `NORMAL`, `HIGH`, or `URGENT`.
- `SymptomRule.explanation` is persisted into the selected risk assessment.
- `AIAdviceBoundary.workflow` attaches the boundary to a workflow.
- `AIAdviceBoundary.stage` optionally scopes the boundary to a care stage.
- `AIAdviceBoundary.allowed_topics` stores model-level allowed advice topics.
- `AIAdviceBoundary.forbidden_topics` stores model-level forbidden advice topics.
- `AIAdviceBoundary.required_disclaimer` stores a disclaimer candidate for patient advice.
- `EscalationRule.symptom_rule` links escalation configuration to one symptom rule.
- `EscalationRule.target_role` can be `DENTIST` or `ADMIN`.
- `EscalationRule.target_role` cannot be `PATIENT` through model choices and serializer validation.
- `EscalationRule.urgency` uses the same choices as appointment priority.
- `EscalationRule.appointment_priority` defines configured appointment priority for the escalation rule.
- `EscalationRule.message` stores a configured escalation message.
- Abstract syntax is represented by Django model entities in `backend/workflows/models.py`.
- Concrete syntax is represented by forms in `WorkflowDetailPage.jsx`.
- Concrete syntax is also represented by the generated DSL preview from `render_workflow_dsl_preview`.
- Static semantics are represented by `validate_workflow`.
- Execution semantics are represented by `assess_report`.
- Model transformation is implemented by the report submission and assessment flow.
- The transformation input is a `FollowUpCase`, an active `TreatmentWorkflow`, and a `SymptomReport`.
- The immediate transformation output includes `RiskAssessment`, `AdviceMessage`, optional `EscalationCase`, and `AuditLog` records.
- Appointment records can be created later by staff/admin from an escalation context.
- The system is an internal DSL because users configure domain concepts instead of writing general code.
- The system is MDE-oriented because the configured model controls runtime behavior.
- The system is not an external textual DSL implementation.
- There is no separate grammar file.
- There is no parser for the generated DSL preview.
- The DSL preview is read-only generated text.
- The generated DSL preview is useful for communication and diagram preparation.
- The generated DSL preview is not the authoritative runtime input.
- The authoritative runtime input is the persisted Django workflow model.

## 6. Static Semantics And Validation
- Static semantics are implemented in `validate_workflow` in `backend/workflows/services.py`.
- The validation result contains `is_valid`, `checks`, `errors`, and `warnings`.
- The current implementation returns an empty `warnings` list.
- The first implemented check is `stages_exist`.
- `stages_exist` fails when the workflow has no care stages.
- The second implemented check is `stage_ranges_valid`.
- `stage_ranges_valid` fails when a care stage has `end_day < start_day`.
- The third implemented check is `stage_ranges_do_not_overlap`.
- `stage_ranges_do_not_overlap` fails when consecutive stages overlap after sorting by day range.
- A stage beginning on the same day that the previous stage ends counts as overlapping.
- The fourth implemented check is `symptoms_exist`.
- `symptoms_exist` fails when the workflow has no symptom definitions.
- The fifth implemented check is `symptom_keys_unique`.
- `symptom_keys_unique` fails when duplicate symptom keys are detected.
- The database also has a unique constraint named `unique_symptom_key_per_workflow`.
- The sixth implemented check is `rules_exist`.
- `rules_exist` fails when the workflow has no symptom rules.
- Condition JSON shape is validated through `validate_condition_shape`.
- The condition object must be a dictionary.
- The condition object must contain exactly one logical group.
- The only supported logical groups are `all` and `any`.
- The group value must be a non-empty list.
- Every group item must be an object.
- Nested groups are allowed.
- Leaf items must contain `field`, `operator`, and `value`.
- The `field` must be a non-empty string.
- Supported operators are `=`, `!=`, `>`, `>=`, `<`, `<=`, and `in`.
- Unsupported operators make condition validation fail.
- The validation report exposes `rule_condition_shape_valid`.
- The validation report exposes `rule_operators_supported`.
- In the implementation, unsupported operators are detected by the same shape validation path.
- The validation report exposes `rule_references_known_fields`.
- Rules may reference symptom keys defined by the workflow.
- Rules may also reference `day_after_treatment`.
- `day_after_treatment` is the only extra allowed report field in workflow validation.
- Unknown condition fields make the workflow invalid.
- The validation report exposes `high_urgent_rules_have_escalation`.
- Every `HIGH` rule must have an `EscalationRule`.
- Every `URGENT` rule must have an `EscalationRule`.
- The validation report exposes `high_urgent_rules_not_advice_only`.

- The validation report exposes `advice_boundary_forbids_prescription`.

- The required forbidden topics are `diagnosis` and `prescription`.
- If either required forbidden topic is missing, validation adds the shared boundary error.
- The validation report exposes `escalations_define_appointment_priority`.

- The validation report exposes `workflow_can_be_activated`.
- `workflow_can_be_activated` is a summary check.
- `workflow_can_be_activated` fails when prior validation errors exist.
- `workflow_can_be_activated` is not added as an extra error message.
- A draft workflow can move to `VALIDATED` only if validation passes.

- A workflow can move to `ACTIVE` only from `VALIDATED`.

- Only active workflows can be archived.
- Static semantics do not validate clinical correctness.
- Static semantics validate model consistency and safety constraints.
- Static semantics do not evaluate patient reports.
- Static semantics do not create advice.

## 7. Execution Semantics
- Execution semantics are implemented by `assess_report` in `backend/decision_engine/services.py`.
- The execution starts when a symptom report is created.
- `SymptomReportSerializer.create` stores the report and calls `assess_report`.
- Staff or patients can also trigger evaluation through `/api/decision-engine/reports/{report_id}/evaluate/`.
- The assessment service is idempotent for an already assessed report.
- If a risk assessment already exists, the service returns it after ensuring downstream outputs exist.
- If an assessment exists but advice or escalation is missing, downstream outputs can be created on reevaluation.
- The report must be saved before assessment.
- The report is loaded with its follow-up case, patient, workflow, and existing assessment context.
- The follow-up case determines the workflow.
- The follow-up case treatment date determines `day_after_treatment`.
- `SymptomReport.save` computes `day_after_treatment` as local date minus treatment date.
- Negative day values are clamped to zero.
- Stage detection queries care stages for the assigned workflow.
- Stage detection requires `start_day <= day_after_treatment <= end_day`.
- Stage detection orders by `sort_order`, `start_day`, and id.
- If more than one stage matched because of invalid data, the first ordered stage would be used.
- Proper validation is expected to prevent overlapping stages before activation.
- If no care stage matches, the system creates a warning assessment.
- The no-stage fallback risk level is `WARNING`.
- The no-stage fallback recommended action is `RECOMMEND_CONTACT`.
- The no-stage fallback appointment priority is `NORMAL`.
- The no-stage fallback explanation tells the patient to contact the clinic.
- If a stage is detected, the engine selects symptom rules for that stage only.
- Rules from other stages are not considered.
- The report values map starts with legacy fixed fields.
- Legacy fixed fields include `bad_smell`, `bleeding`, `fever`, `pain_level`, and `swelling`.
- If `report.symptom_values` is a dictionary, the decision engine merges those dynamic values into the report values map.
- Dynamic `symptom_values` override same-named legacy fixed values in the runtime value map.
- The engine then adds `day_after_treatment`.
- Rules can therefore reference legacy fields, dynamic workflow symptom keys, and `day_after_treatment`.
- The engine validates each rule condition shape before evaluating it.
- Malformed rule conditions do not crash evaluation.
- Malformed rule conditions simply do not match.
- The engine evaluates `all` groups with logical AND.
- The engine evaluates `any` groups with logical OR.
- The engine evaluates nested groups recursively.
- The `=` operator checks equality.
- The `!=` operator checks inequality.
- The `>` operator checks greater-than.
- The `>=` operator checks greater-than-or-equal.
- The `<` operator checks less-than.
- The `<=` operator checks less-than-or-equal.
- The `in` operator checks whether the actual value is in the expected value.
- Type errors during comparison make the condition false.
- Unknown runtime fields make the condition false.
- Matching rules are collected in stage rule order.
- If no rules match, the system creates a low-risk fallback assessment.
- The no-rule fallback risk level is `LOW`.
- The no-rule fallback recommended action is `CONTINUE_MONITORING`.
- The no-rule fallback appointment priority is `NONE`.
- The no-rule fallback explanation states that no symptom rule matched in the detected stage.
- The no-rule fallback is deterministic but clinically conservative only to the extent that the workflow contains adequate safety-net rules.
- A severe symptom such as pain level 10 can fall back to `LOW` if no rule in the detected stage matches that symptom.
- Robust workflow design should include stage-level red-flag rules for single dangerous symptoms such as severe pain, heavy bleeding, fever, discharge, visible bone, lost clot, breathing difficulty, or persistent numbness.
- Workflow authors should not model every possible symptom combination.
- Workflow authors should combine broad safety-net rules with more specific combination rules.
- If rules match, the selected rule is the rule with the highest severity.
- Severity order is `LOW`, `WARNING`, `HIGH`, `URGENT`.
- If multiple rules have equal severity, Python `max` returns the first one encountered in the ordered list.
- The selected rule's risk level is persisted.
- The selected rule's recommended action is persisted.
- The selected rule's appointment priority is persisted.
- The selected rule's explanation is persisted.
- All matched rule traces are persisted in `RiskAssessment.matched_rules`.
- The matched rule trace includes id, name, risk level, recommended action, appointment priority, and explanation.
- The matched rule trace does not store the full condition.
- `RiskAssessmentSerializer` reconstructs condition text from the live `SymptomRule` when possible.
- The created risk assessment records the detected stage if one exists.
- The created risk assessment has a one-to-one relationship with the report.
- After creating a risk assessment, the decision engine records an audit log.
- The audit action is `RISK_ASSESSMENT_CREATED`.
- The audit details include report id, risk level, recommended action, appointment priority, and matched rule ids.
- After creating the assessment, downstream output generation is invoked.
- Downstream output generation calls `generate_advice_for_assessment`.
- Downstream output generation calls `create_escalation_for_assessment`.
- Advice is generated for all risk levels.
- Escalation is generated only for `HIGH` and `URGENT`.
- Appointment records are not automatically created by report assessment.
- Appointment priority is persisted on the assessment for later appointment handling.
- Staff/admin can create an appointment from an escalation.
- Audit records are created for report submission, assessment creation, advice creation, escalation creation, case status changes, appointment creation, and appointment updates.

## 18. Implementation Uncertainties And Limitations Found
- The project contains strong workflow-model behavior, but it is implemented as an internal Django model DSL rather than an external DSL parser.
- The generated DSL preview is display-only.
- Runtime rule evaluation supports fixed legacy fields, dynamic workflow symptom values, and `day_after_treatment`.
- Workflow symptom definitions now extend the patient report schema through the generated patient report form.
- The dynamic report form is still bounded by admin-defined workflow symptom definitions.
- `EscalationRule` is important to validation and DSL preview.
- `EscalationRule` fields are not fully consumed by runtime escalation creation.
- The staff escalation form filters high/urgent rules needing escalation, but runtime escalation creation still uses the final risk assessment rather than loading the configured escalation rule message or target role.
- Advice generation uses templates only.
- Advice generation does not use an LLM.
- Advice generation does not use `allowed_topics` to select message content.
- Advice generation uses the required disclaimer if safe.
- Appointment creation is staff/admin initiated after escalation.
- Appointment creation is not automatic during report assessment.
- Editing an active or archived workflow moves the same workflow record back to draft.
- The system does not implement workflow version cloning.
- Existing follow-up cases assigned to that workflow can be affected by future reactivation of the edited workflow.
- Existing risk assessments are not automatically recomputed when a workflow is edited.
- The no-rule fallback is `LOW`; robust clinical workflow design requires safety-net rules for dangerous symptoms.
- Admin Intelligence is a deterministic operational assistant.
- Admin Intelligence is not the workflow DSL engine.
- Admin Intelligence is not a medical assistant.
- Formal GoF Factory Method, Abstract Factory, and Proxy patterns are not implemented as class-pattern structures.
- Any later design-pattern diagrams should label conceptual mappings clearly or mark those patterns as future work.
